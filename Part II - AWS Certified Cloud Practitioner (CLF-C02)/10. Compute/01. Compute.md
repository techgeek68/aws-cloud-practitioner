Compute is the largest service family on the CLF-C02 exam and the one most people meet first. This chapter covers instances, containers, and serverless, then works through four labs.

## 10.1 The AWS Compute Portfolio

| Service | Model | Characteristics | Effort |
| --- | --- | --- | --- |
| Amazon EC2 | IaaS, virtual machines | Full control of the operating system and environment | Highest, and the most flexible |
| Amazon ECS, EKS, and AWS Fargate | Container orchestration | Scales well; Fargate removes the instances entirely | Moderate |
| AWS Lambda | Serverless, event driven | No servers to manage, pay only for execution time | Lowest, within its constraints |
| AWS Elastic Beanstalk | PaaS for web applications | Provide code, AWS provisions and manages the rest | Low, quick to start |

The wider portfolio also includes Amazon EC2 Auto Scaling, Amazon ECR, Amazon Lightsail, AWS Batch, AWS App Runner, AWS Outposts, and the AWS Serverless Application Repository.

**Choosing between them** comes down to four questions:

- How much control over the operating system does the application need?

- Is the workload continuous, spiky, or event driven?

- Is the application already containerized, or could it be?

- How much operational effort is the team able to sustain?

## 10.2 Amazon EC2 Fundamentals

Amazon Elastic Compute Cloud provides resizable virtual servers called instances. You control the operating system, networking, storage, and scaling, without owning hardware.

EC2 suits workloads needing persistent always on compute, fine grained environment control, or anything that does not fit a serverless or container model, including legacy applications, custom runtimes, and high performance computing.

### 10.2.1 Amazon Machine Images

An AMI is the template an instance launches from. It contains:

- A root volume template, meaning the operating system and any preinstalled software.

- Launch permissions controlling which accounts may use it.

- Block device mappings defining the volumes attached at launch.

AMIs can be shared between accounts and copied between Regions. AMI strategy for production is covered in section 19.4.

### 10.2.2 Instance Families and Sizes

An instance type name such as `m5.large` breaks down as family, generation, and size.

| Family | Optimized for | Typical workload |
| --- | --- | --- |
| General purpose (T, M) | Balanced CPU, memory, and network | Web servers, small databases, development |
| Compute optimized (C) | High CPU relative to memory | Batch processing, media transcoding, gaming servers |
| Memory optimized (R, X, Z) | Large memory relative to CPU | In-memory databases, large caches, analytics |
| Storage optimized (I, D, H) | High local disk throughput and IOPS | Data warehouses, distributed file systems |
| Accelerated computing (P, G, Inf, Trn) | GPUs or purpose-built accelerators | Machine learning training and inference, graphics |

T-family instances are burstable: they accumulate CPU credits while idle and spend them under load. That makes them cheap for uneven low-average workloads and a poor choice for anything with sustained high CPU.

### 10.2.3 Instance Lifecycle

```
pending -> running -> stopping -> stopped -> shutting-down -> terminated
                  \-> rebooting -/
```

- Only EBS-backed instances support the `stopped` state. Instance store-backed instances go straight to `terminated`.
- Stopping halts compute charges. EBS storage charges continue.
- Stopping and starting almost always moves the instance to a different physical host, which is why instance store data does not survive it.
- Rebooting keeps the instance on the same host and preserves instance store data.

### 10.2.4 Instance Metadata

Every instance can read its own runtime details from a link-local endpoint:

```
http://169.254.169.254/latest/meta-data/
```

Available values include the instance ID, instance type, private and public addresses, hostname, security groups, Region, and Availability Zone.

Use **IMDSv2**, which requires a session token obtained by a PUT request before any metadata read. IMDSv1 answered a plain GET, which made it reachable through server-side request forgery. IMDSv2 is the default for new instances and should not be disabled.

### 10.2.5 Monitoring

- **Basic monitoring** is enabled by default, free, and publishes metrics every 5 minutes.

- **Detailed monitoring** publishes every 1 minute for an additional charge.

- Memory and disk utilization are not published by default, because the hypervisor cannot see inside the guest. The CloudWatch agent is required for those.

CloudWatch itself is covered in section 13.2.

## 10.3 EC2 Storage Options

| Option | Type | Persistence | Use |
| --- | --- | --- | --- |
| Amazon EBS | Block, network attached | Survives stop, start, and termination if the delete-on-termination flag is cleared | Root volumes, databases, anything needing durable block storage |
| Instance store | Block, physically attached to the host | Lost on stop or terminate, survives reboot | Scratch space, caches, buffers, replicated data |
| Amazon EFS | Shared file | Independent of any instance | Content shared by many instances at once |
| Amazon S3 | Object | Independent of any instance | Backups, static assets, data lakes |

The distinction that matters: **instance store is ephemeral**. It is fast and included in the instance price, and everything on it disappears the moment the instance stops. Storage is covered in full in Chapter 11.

## 10.4 Elastic IP Addresses

- A static public IPv4 address allocated to your account and held until you release it.

- Can be remapped to any instance or network interface in the account, which makes it useful for a fixed endpoint or for a NAT gateway.

- Survives instance stop and start, unlike an auto assigned public IP.

- **Billed while allocated but not associated with a running instance.** This is one of the most common unexpected charges in a study account.

Where a fixed address is not strictly required, a DNS name pointing at a load balancer is usually the better design.

## 10.5 EC2 Pricing Models

| Model | Commitment | Discount | Best for |
| --- | --- | --- | --- |
| On-Demand | None | None | Spiky, unpredictable, or short lived workloads |
| Reserved Instances | 1 or 3 years, all, partial, or no upfront | Substantial against On-Demand | Steady state predictable usage |
| Savings Plans | 1 or 3 years, committed spend per hour | Comparable to Reserved Instances, with more flexibility | Steady usage where instance family or Region may change |
| Spot Instances | None, but interruptible | Up to 90% against On-Demand | Fault tolerant, flexible, time insensitive work |
| Dedicated Instances | None or reserved | Premium price | Hardware not shared with other customers |
| Dedicated Hosts | None or reserved | Premium price | Bring-your-own-license and strict compliance |

Points worth knowing precisely:

- **Spot is not an auction.** AWS set the price by supply and demand and removed the bidding model in November 2017. You may set a maximum price, and AWS reclaims the capacity with a two-minute warning.

- **Savings Plans cover more than EC2.** Compute Savings Plans apply to EC2, AWS Lambda, and AWS Fargate, which is why they are usually the better default than Reserved Instances.

- **Dedicated Instances versus Dedicated Hosts.** Both give single-tenant hardware. Only Dedicated Hosts give visibility of the physical sockets and cores, which is what per-socket licensing requires.

- Scheduled Reserved Instances were discontinued on September 3, 2024. AWS now recommends On-Demand Capacity Reservations combined with Savings Plans for recurring capacity needs.

## 10.6 The Four Pillars of EC2 Cost Optimization

1. **Right size.** 

Match the instance to what the workload actually uses. CloudWatch metrics and AWS Compute Optimizer identify overprovisioned instances. This is usually the largest and easiest saving.

2. **Increase elasticity.** 

Stop or hibernate instances outside working hours, and let Auto Scaling remove capacity when demand falls. Non-production environments running nights and weekends are pure waste.

3. **Choose the optimal pricing model.** 

Mix On-Demand, Spot, and commitment based pricing to match the shape of the workload, and consider serverless where the workload is intermittent.

4. **Optimize storage.** 

Select the right EBS volume type, delete unattached volumes and stale snapshots, and apply S3 lifecycle policies.

**Making it stick**

- Tag resources consistently so cost can be attributed to a team, environment, or project.

- Set performance and cost targets and measure against them.

- Give someone ownership of the review, or it will not happen.

## 10.7 Containers on AWS

### 10.7.1 Containers and Docker

A container packages an application with its runtime, libraries, and configuration into one portable unit using operating system level virtualization.

| Aspect | Containers | Virtual machines |
| --- | --- | --- |
| Isolation boundary | Operating system kernel, shared | Hypervisor, full guest OS each |
| Startup | Seconds | Minutes |
| Density | Many per host | Fewer per host |
| Overhead | Small | A full operating system per instance |

Docker is the standard tooling for building and running them. A container image bundles code, runtime, libraries, and configuration so it behaves identically wherever it runs.

### 10.7.2 Amazon ECS

AWS's own container orchestrator, integrated with IAM, security groups, EBS, and Elastic Load Balancing.

- **EC2 launch type.** 

You provision and manage the container instances, which gives control over instance type and lets you use Reserved Instances or Spot.

- **Fargate launch type.** 

AWS runs the infrastructure. You declare CPU and memory per task and never see a host.

### 10.7.3 Amazon EKS

Managed Kubernetes. AWS runs the control plane and you run workloads on managed node groups or on Fargate. The right choice when you already use Kubernetes or need portability across environments; otherwise ECS is simpler.

### 10.7.4 Amazon ECR

A managed private container registry with image scanning, lifecycle policies, IAM-based access control, and native integration with ECS and EKS.

Container architecture trade-offs are covered in section 19.5.

## 10.8 AWS Lambda

Lambda runs code in response to events with no servers to provision or manage, and bills only for execution time.

**Benefits**

- Write in a supported language you already use.

- AWS handles infrastructure, patching, scaling, and availability.

- Native integration with AWS event sources and orchestration services.

- No charge when the function is not running.

**Common event sources**

Amazon S3, Amazon DynamoDB Streams, Amazon SNS, Amazon SQS, Amazon API Gateway, Amazon EventBridge and EventBridge Scheduler, and direct invocation from an application.

**Function configuration**

Code and dependencies, an IAM execution role, memory allocation, a timeout, and automatic logging to CloudWatch Logs. CPU is allocated in proportion to memory, so raising memory also raises CPU.

**Default quotas per Region**

| Quota | Limit |
| --- | --- |
| Concurrent executions | 1,000, a soft limit that can be increased |
| Function and layer storage | 75 GB |
| Maximum memory | 10,240 MB |
| Maximum execution duration | 15 minutes |
| Deployment package, unzipped | 250 MB |
| Container image size | 10 GB |

**Typical use cases**

- Schedule based, such as starting or stopping EC2 instances on a timer, which is built in section 10.14.

- Event based, such as generating a thumbnail when an image lands in S3.

Serverless design, including cold starts and concurrency, is covered in section 19.6.

## 10.9 AWS Elastic Beanstalk

A platform as a service that provisions and manages the infrastructure for a web application, so a developer supplies code and configuration only.

- **Supported platforms:** 

Java, .NET, PHP, Node.js, Python, Ruby, Go, and Docker.

- **What it creates:** 

EC2 instances, an Auto Scaling group, a load balancer where required, security groups, and CloudWatch alarms.

- **What you keep:** 

Full access to the resources it creates. Beanstalk is a convenience layer over ordinary AWS services, not a black box.

- **Cost:** 

Beanstalk itself is free. You pay for the resources it provisions.

It fits teams that want a deployment pipeline without building one, and standard web applications in a supported runtime. It is the wrong fit when the architecture needs resources Beanstalk does not model, at which point CloudFormation or Terraform is the better tool.

## 10.10 Other Compute Services

- **AWS Batch.** 

Runs batch jobs at any scale, provisioning and scaling compute automatically, including Spot capacity.

- **AWS App Runner.** 

Builds and runs a containerized web application or API directly from source or an image, with no infrastructure configuration.

- **Amazon Lightsail.** 

Bundled virtual servers at a fixed monthly price, aimed at simple sites and small applications.

- **Amazon EC2 Auto Scaling.** 

Adds and removes instances to match demand, covered in section 13.3.

- **AWS Outposts.** 

AWS-managed racks in your own facility, covered in section 5.5.
